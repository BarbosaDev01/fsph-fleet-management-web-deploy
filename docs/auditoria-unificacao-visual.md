## Contratos de viagem: diferenças obrigatórias

| Recurso     | Staging publicado                                                                                                 | Main oficial / consolidado                                        | Consequência                                                                                                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Transport   | `/transports`, ocorrência/serviço/origem/destino, paginação; PENDING/ASSIGNED/COMPLETED/CANCELLED                 | Sem controller Transport                                          | Manter módulo e tipos legados; não trocar sua entidade.                                                                                                                             |
| Route       | `/routes`, cronograma com duração/retorno, paradas, início/conclusão/cancelamento                                 | Sem controller Route                                              | Não converter UUID, estados ou paradas para Trip. Compatibilidade restrita ao backend que oferece esse contrato.                                                                    |
| TripRequest | `/trip-requests`, mine, availability, eligible-vehicles, calendar; criar/editar/cancelar/aprovar/rejeitar/agendar | Mesma família canônica; verificar diferenças por DTO/controller   | Formulário próprio: departureAt, expectedReturnAt, origin, destination, purpose, passengerCount, requestedVehicleId opcional. Estados PENDING/APPROVED/REJECTED/SCHEDULED/CANCELED. |
| Trip        | POST `/trips`, PATCH completion, GET histórico                                                                    | Histórico consolidado paginado, filtros e autorização específicos | Registro de execução OPEN/COMPLETED; sem cancelamento nem paradas. Não confundir resposta paginada consolidada com retorno do staging.                                              |

As permissões são retornadas por `/auth/me`; nome do papel não autoriza todas as ações. Leitura, escrita e gerenciamento têm autoridades distintas. `mine`, edição e cancelamento respeitam propriedade. O backend continua sendo a autoridade para regras de setor, CNH, manutenção, capacidade, conflitos e concorrência. A UI não deve inventar escopo setorial que a API não fornece.

O editor de permissões anterior usa catálogo estático, com risco de omitir autoridades novas ao substituir a lista inteira. Preservar permissões retornadas que o cliente desconhece e restringir gravação a PERMISSIONS_WRITE.

## Diagnóstico visual

`AppLayout`, `FleetLayout`, `DashboardSidebar`, sidebar SVO e sidebar do dashboard de usuários competem pela navegação. Há cabeçalhos com usuários fictícios dentro de sessão JWT válida. CSS de dashboards/solicitações/SVO repete fundos, bordas, fonte e tamanhos; CSS específico de gráficos/tabelas precisa ser preservado. Os componentes `PageHeading`, `DataTable`, `FormDialog`, `ActionForm`, `ApiFeedback` e o tema MUI já atendem os módulos reais e serão a base comum.
